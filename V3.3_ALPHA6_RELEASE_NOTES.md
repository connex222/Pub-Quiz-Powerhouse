# Pub Quiz Powerhouse v3.3 Alpha 6 — Multiplayer Approval Reliability

**Status:** DEVELOPMENT BUILD / NOT PRODUCTION READY.

## What changed since Alpha 5

- The quizmaster's Approve button becomes disabled while a phone assignment is awaiting server confirmation. Repeated clicks cannot create duplicate teams.
- New teams are created **only after** the relay confirms the phone assignment; a failed connection no longer produces a team with no approved phone.
- New-team approvals are serialised to prevent simultaneous requests from creating identically named teams or exceeding the configured team limit.
- Approval acknowledgements have a **6.5-second deadline**. A lost acknowledgement can no longer leave the button blocked indefinitely. A late acknowledgement is ignored.
- Cancellation/rejection while the server assignment is still pending cancels the local approval and requests restoration of the prior relay team binding.
- Outdated acknowledgements from an earlier room or replaced connection are ignored.
- Added regression tests for these cases, plus a one-click Windows integration-test runner (`run-release-checks.bat`).

## Run the real Socket.io integration test on Windows

1. Download and extract Alpha 6 into a new folder (outside OneDrive if possible).
2. Double-click **`run-release-checks.bat`**. It installs dependencies on first run (requires an internet connection) and then runs `npm test`.
3. Check for **ALL TESTS PASSED**, and retain `LIVE_TEST_RESULTS.txt` for error diagnosis. This runner uses localhost and does not change GitHub or Render.
4. If the test fails, stop and send the log rather than promoting the build.

## Live-device acceptance matrix (must still be performed)

- [ ] **Classic:** Host opens a quiz on staging Render; phone A and phone B join with approval; both submit answers; everyone marked correctly earns points.
- [ ] **Quizmaster refusal:** Reject a fresh phone, verify it cannot buzz or see a private reply for another team.
- [ ] **New team:** Approve a new team, verify it appears exactly once and only after approval.
- [ ] **Reconnection:** Put phone A into airplane mode, restore its network, and verify it rejoins the assigned team while the host session stays alive.
- [ ] **TV pairing:** Pair the TV, show a question, change question, reveal results, refresh the TV and verify reconnection.
- [ ] **Game Show:** Two phones buzz almost at once: only the first accepted phone is active; mark it wrong, then allow another team; award points and verify scores.
- [ ] **Host refresh:** Reload the host mid-question; verify question position, scores and history return. Phone reapproval may be required after host browser refresh.
- [ ] **Render restart:** Expect session/room state to be lost on a new instance. Phones may need to rejoin and TVs to re-pair. This is a documented limitation, not proof of automatic failover.
- [ ] **Sound:** Confirm the uploaded music and effects play when browser audio is unlocked on the test devices.
- [ ] **Complete night:** Finish both a Classic Quiz and a TV Game Show; check winners, corrections, leaderboard, and no duplicate scoring.

## Deployment boundaries

Use the existing **`feature/v3.3-dual-experience`** GitHub development branch for Alpha 6. Do not merge it into `main` yet. A dedicated Render staging service should deploy that branch, while the live Render service stays on `main`. Neither hosting deployment nor live-device testing is performed by this ZIP.

## Known limitations

The host browser is still the authoritative in-memory game state. The Render relay's pairing and authentication data are ephemeral. This build is only suitable for one running server instance, not a highly available or multi-server cluster. Approved Idle art is still missing; idle views continue to use the Correct portrait as a fallback.
