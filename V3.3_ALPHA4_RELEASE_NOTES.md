# Pub Quiz Powerhouse v3.3 Alpha 4 — Multiplayer Reliability & Security

**Release status:** Development alpha. This is not the production release or a claim that live Render devices have been tested. Keep v3.2 live until manual testing on phones/TV is complete.

## Changes since Alpha 3

### Relay-side validation

- Every phone now registers with a **cryptographically random 256-bit per-phone secret**, saved locally on that phone. The server binds that credential to its phone ID within the room.
- Incoming phone messages must originate from a registered socket. The server rejects forged phone IDs, unauthorised message types, oversized payloads, and answers claiming a different team than the phone's server-approved team assignment.
- The quizmaster explicitly assigns the chosen team to a registered phone before notifying the phone that joining succeeded.
- Each phone can subscribe only to its own private `out/<phoneId>` channel. Only the room owner can listen to the incoming answers channel or broadcast state, replies, and TV data.
- TV channels require a completed host/TV pair or a successful resume using the paired secret; knowing a public room code alone is insufficient.
- Only public phone state and paired screen state can be retained; private messages are never retained.
- Single-use TV pairing codes, message-size restrictions and socket rate limits remain in place.

### Reconnect and reliability

- On reconnect, a phone must re-authenticate **before** re-subscribing to its private reply channel or sending a saved-team join message.
- The quizmaster must reclaim its room **before** subscribing to answer messages or publishing question state; previously these operations could race.
- Returning phones with the same local private secret can resume their old phone identity and team assignment when the relay instance remains running.
- After a temporary Render restart, phones retry authentication while the host reclaims the room.
- A TV refresh resumes its paired screen grant if the server still holds it. If a server restart loses the grant, the TV clears the stale pairing and displays a new code so the host can pair it again.
- Previous Classic scoring, the exclusive game-show buzzer, avatars, music, quiz packs, and saved scores remain unchanged.

## What this does NOT solve yet

1. **Public join-link team selection:** guests can still *select* another existing team through the normal team chooser. The new server validation stops a phone from falsifying its identity in a message after pairing, **not** deliberate selection of a team in the UI. An optional host-approved or team-PIN join flow is recommended before public pub events.
2. **Server-authoritative scoring:** the host browser is still trusted to run the quiz. Its state is not persisted in a hosted database.
3. **Render replicas:** the room registry, live phone sessions and TV pairing grants are in server memory, so this deployment must run as **one instance**; redis-backed adapters and persistent session storage are beyond Alpha 4.
4. **Server restart and TV:** previously paired TVs must enter a fresh one-time pairing code after a server restart.
5. **Actual mixed Wi-Fi/mobile real-device proof:** not tested by the offline automated suite. iOS Safari, Android Chrome, TV browsers, mobile data, recovery while buzzing, and live Render redeploys still require human test runs.

## Automated tests performed

- `npm run test:offline`: relay protocol authorization mock, browser client reauthentication order, scoring/migration, question lifecycle, exclusive buzzer rules. These run without Socket.io dependencies.
- `python test/browser-smoke.py`: Classic lifecycle, scoring corrections and reload.
- `python test/browser-experiences.py`: Classic and Show scoring and typed answers.
- `python test/browser-show-exclusive.py`: exclusive claim, ineligible team, penalty, rollback, timeout and replay.
- JavaScript syntax tests and archive integrity checks.

**Not executed in this environment:** `npm test` real Socket.io integration, because the needed npm dependency packages were unavailable locally and online installation timed out. `test/relay.js` is updated to the new protocol and must run on a Windows machine with `npm install` completed before release.

## Manual on-device verification (before merge)

1. Keep live v3.2 running; extract Alpha 4 to its own folder on Windows and run `start.bat`.
2. Choose phone play and open a TV at `/tv`; enter the four-digit code in the quizmaster. Confirm the TV mirrors the game.
3. Join two phones as **different teams**. Start Classic. Both should submit a correct answer, and both should get the full points. Check Wrong/Correct avatars.
4. Reload one phone after it has joined; it should return to the same team. Repeat after switching Wi-Fi off/on, when possible.
5. Refresh the TV and confirm it reconnects without a new code when the server is still running.
6. Start TV Game Show with a buzzer round. Buzz first on one phone, verify the other locks. Mark the first wrong and have the second buzz; only the second should then score.
7. Close and restart `start.bat` while the phone/TV browsers remain open; check that the host resumes, phones recover, and the TV shows a **new pairing code**, which must be entered again.
8. Test a host browser refresh: questions/scores should recover from local storage. **Do not assume a different computer can recover them.**
9. Run `npm test` in the extracted folder; all tests must pass before declaring Release Candidate 1.

## Important deployment guidance

- Do **not** push Alpha 4 onto GitHub `main` or deploy to your current live Render service until all manual checks pass.
- The existing `feature/v3.3-dual-experience` branch can be used for staging after approval.
- Run one Render instance only. Use a separate staging service and a distinct staging URL for network QA.
- Team-specific PINs/host approval and durable server state should be tracked as explicit remaining work.
